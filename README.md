# avio-cast

보드가 cast 로 내보내는 카메라 스트림을 PC 에서 **라이브 입력 소스**로 받는 avio 드라이버.

보드는 녹화용으로 이미 한 번 인코딩한 패킷을 그대로 TCP 로 티핑한다(`drv/avsink-mpp`,
`avsink_cast.h`). 이 드라이버는 그 선의 반대쪽 끝이다. 채널 하나가 디바이스 하나이고,
호스트가 보기에는 평범한 라이브 avio 소스다 — avio-v4l2 와 다른 점은 케이블이 USB 라는
것뿐이다.

```
보드: capture -> MPP encode -+-> MKV 파일   (rec)
                             +-> TCP 소켓   (cast)
                                       |
PC:                    avio-cast <-----+  -> LBX_IMAGE (YUV 평면)
```

이게 되면 **보드에 녹화 → 매체로 옮기기 → PC 에서 재생** 왕복이 사라진다. 모형차 카메라
영상이 알고리즘에 곧바로 들어간다.

수신·디코드 코어의 출처는 `tool/clink`(`clink_cast.cpp`)다. clink 은 제어면(무엇을 언제
켤지)만 남기고, 이 드라이버의 첫 소비자가 된다. 사본을 두지 않는다.

## 구조

| 파일 | 책임 |
|---|---|
| `avio_cast_main` | AVIO vtable → core. AVIO 타입을 아는 유일한 파일 |
| `avio_cast_ui` | ProcessUI 패널 — 채널별 링크 상태·fps·오류 |
| `cast_core` | 링·refcount·drain-to-latest·패킷 탭. 순수 상태 |
| `cast_link` | 전송 — adb forward, 채널당 TCP demux 스레드 |
| `cast_dec` | 디코더 백엔드 seam (avcodec, 나중에 gst) |

`avio_play_main → play_core` 와 같은 분리다. 코어는 드라이버 타입을 모른다.

## 계약

- **포트**: `base_port + slot`. 슬롯 0 = 보드 화면, 카메라는 슬롯 1 부터
  (avsink `cast.caps`). 기본 base_port 25560.
- **디바이스 id**: `"cam0".."cam7"`, `"screen"`.
- **링 깊이 8**. avio-v4l2 `NUM_VIDBUF` 와 같은 값이다. 프레임은 표시만 하는 게 아니라
  알고리즘이 여러 장 쥔다 — 그래서 refcount 링이 기본이고, 단일 "최신 프레임" 슬롯은
  읽는 중에 덮인다. 이 링을 8→3 으로 줄였다가 FPS 요동을 만든 전례가 있다
  (`lbx-gfx doc/plan-frame-export-seam.md` §15).
- **색변환 없음**. I420/NV12 그대로 올리고 GPU 가 변환한다. 픽셀당 1.5B vs BGRA 4B.

## 호스트와의 경계

전송은 드라이버가, 정책은 호스트가.

- `adb forward` 는 드라이버가 깐다. 정책이 아니라 USB 로 붙은 보드의 포트에 닿는
  방법이고, 포워드가 없으면 죽은 보드와 증상이 구별되지 않는다(연결 실패, 그림 없음,
  로그 없음). 그 오진을 막을 책임은 전송을 아는 쪽에 있다.
- **켜고 끄기는 드라이버 밖**이다. 몇 채널을 흘릴지는 대역폭 판단이고(ADB USB2 실효
  ~205Mbps), 무엇을 보고 있는지는 호스트만 안다. 호스트가 자기 제어 링크로 보낸다
  (clink 의 `s1`/`s0`).

## 페이즈

### P1 — 영상 수신 (지금)

clink 에 먼저 붙여 검증하고, 그다음 svmdemo 로 가져간다. 녹화는 넣지 않는다.

### P2 — 주행 데이터 경로 + PC 직접 저장

지금 선을 타는 건 영상 패킷뿐이다. 하지만 세션은 영상만이 아니다 — DVRS 세션은
프레임마다 딸린 **메시지 스팬**(CAN 휠펄스·GPS·GSEN)을 함께 담고, avio-play 는 재생할 때
그 스팬을 프레임에 맞춰 되돌려준다. 그게 없으면 PC 가 받아 적은 것은 완전한 세션이
아니라 그림 뭉치다.

모형차에서는 큰 의미가 없다. **실차에서 저장 매체 없이 노트북에 직접 받아 적을 때**
의미가 있다 — 그때 필요한 건 영상과 같은 시계를 타는 메시지 경로다.

- svmdemo 의 `drivers.telemetry` 는 이미 있지만 버스 메시지를 UDP/JSON 으로 **뷰어에
  송출**하는 용도다. 세션 저장용 무손실 경로로 설계된 것이 아니다.
- 저장 자체는 **재인코딩이 아니라 mux** 다. 보드가 레코더의 패킷을 그대로 흘려보내므로
  PC 쪽 녹화는 그 패킷을 컨테이너에 쓰는 일이다. 그래서 채널 스레드는 디코더에 먹인
  패킷을 버리지 않고 `CAST_PACKET_FN` 탭으로 닿게 남겨 둔다 — P2 가 여기에 붙는다.
- clink 에도 어차피 녹화가 필요해진다. 같은 길이다.

### P3 — 디코더 seam 을 lbx 로

`cast_dec.h` 는 `avio-play/src/play_dec.h` 와 같은 계약을 의도적으로 복제한 것이다.
같은 파이프의 반대쪽 끝이라 패킷 형식·codec id·CodecPrivate·프레임 레이아웃이 전부 같다.
cast 가 돌아 계약이 두 번째 소비자를 견딘 걸 확인한 뒤 lbx 로 올리면, 두 드라이버가 한
벌을 include 하는 파일 이동으로 끝난다. 검증 전에 올리면 확인 안 된 인터페이스를 못 박고
전 체인 배포를 끌고 온다. 그때까지 두 파일은 같이 고친다.

## 빌드

Windows 전용이다. 보드가 자기 cast 를 받을 이유가 없고, 디코더가 PC 쪽 의존(libav*)이다.
`FFMPEG_SDK` / `GSTREAMER_1_0_ROOT_MSVC_X86_64` 환경변수를 쓴다.

```
build/vs/avio-cast.sln
```
